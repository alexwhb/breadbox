# Lesson format

Lessons are TOML files read by `bb-lessons` (`crates/bb-lessons/src/format.rs` is the
authoritative schema). Each one starts from a real bb-circuit project, walks through steps of
eight kinds, and checks every goal against the circuit, the running bench or a SPICE analysis.
Every lesson ships with a **worked solution**; `cargo test -p bb-lessons --test solver` replays
the solutions of all built-in lessons on a headless bench, so a lesson that can't be
completed fails CI.

## Layout

```
lessons/
  1-electricity/
    track.toml                    the track
    03-ohms-law-led.toml          a lesson (any *.toml other than track.toml)
    ohms-law-led.bench.json       its start circuit (a bb-circuit project)
    sketches/<name>/<name>.ino    sketches used by the lessons (sketch.yaml names the board)
    firmware/<name>.uno.hex       prebuilt AVR images (lessons/build-firmware.sh)
  2-sensors/ …
```

Folder names only sort; the ids inside the files matter. Lessons are ordered by `order`.
Lesson packs (plugins) use the same layout under the folder named by `provides.lessons` (see
[Lesson packs](#lesson-packs)).

### `track.toml`

```toml
id = "electricity"
title = "Electricity you can see"
label = "Track 1 · Electricity you can see"   # header of the Lessons screen
order = 1
description = "…"
```

## A lesson

```toml
id = "ohms-law-led"            # unique across all tracks
track = "electricity"          # the track's id
order = 3                      # "Lesson 3 of 8"
title = "Ohm's law with an LED"
summary = "…"                  # one line for the track list
minutes = 12

[bench]
project = "ohms-law-led.bench.json"   # start circuit next to the lesson, or
# example = "garden-node"             # an example project (examples/<id>)
warmup = 0.5                          # bench seconds before step 1 (optional)
[bench.world]                         # world variables at the start (optional)
"light.ambient_lux" = 1000.0
[bench.firmware]                      # extra MCU images: part id → file (optional)
u1 = "firmware/blink.uno.hex"

[[steps]]
…
```

**Start circuit.** A `bb_circuit::Project` JSON file (what `Project::save` writes). MCU parts
reference their sketch and prebuilt image relative to the lesson folder
(`"firmware": { "sketch": "sketches/blink", "image": "firmware/blink.uno.hex" }`); API-level
boards (ESP32, Pico, `fqbn = breadbox:host:*`) are built from the sketch with the host
compiler when the lesson starts. Part ids are the lowercase designators (`r1`, `dmm1`) and are
what checks and actions refer to. Pro-mode projects (`"mode": "pro"`) run no bench; their
steps are checked with SPICE.

The built-in start circuits are generated by
`cargo run -p bb-lessons --example write_benches` (`BenchBuilder` circuits, or snapshots of
`examples/` projects with their sketches and images copied next to the lessons).

## Steps

Every step has a `kind`, a `title` and optional content:

| field | |
|---|---|
| `body` | Markdown shown in the step panel |
| `formula` | one line in the formula box (`I = (5.0 V − 2.0 V) ÷ R`) |
| `callouts` | `[[steps.callouts]] part, title, text`: canvas callouts pointing at a part |
| `checks` | goals; all must pass to finish the step ([Checks](#checks)) |
| `run` | bench seconds to run after the worked solution, before checking |
| `hints` | hints shown on request (strings) |
| `solution` | the worked solution ([Actions](#actions)) |
| `vars` | numbers for expressions and templates (`R1 = 1000.0`) |
| `damage_title`, `damage_text`, `repair_label` | the "a part died" card (`Pop. That LED is gone.`) |
| `next_label` | Next button label (default `Next: <next step's title in lower case>`, `Finish lesson` at the end) |
| `choice`, `predict`, `measure`, `table`, `quiz`, `code` | see below |

### Kinds

| kind | what the student does | needs |
|---|---|---|
| `explain` | reads | nothing |
| `build` | changes the circuit | `checks` |
| `predict` | enters a number before measuring | `predict` |
| `measure` | reads an instrument | `measure` or `checks` |
| `experiment` | tries values / interacts with the bench | `choice` or `checks` |
| `break` | breaks something on purpose | a `damaged` check |
| `quiz` | answers a multiple-choice question | `quiz` |
| `code` | writes and uploads a sketch | `code` |

Steps that ask the student to *do* something (`build`, `code`, `experiment`, `break`,
`predict`, `quiz`) need a `solution`.

### `choice`: pick a value

```toml
[steps.choice]
label = "Pick R1"
part = "r1"                # the part …
prop = "resistance"        # … and property the options set
var = "R"                  # the value's name in expressions (default "R")
default = 1                # option selected on entering the step
options = [
    { label = "100Ω", value = 100 },
    { label = "220Ω", value = 220 },
    { label = "None", value = 0, bypass = true },   # replace the part by a wire
]
```

Picking an option sets the property (a live parameter change on the bench); `bypass` sets the
property's minimum (a resistor becomes 0.01 Ω). The option's label is the template variable
`{choice}`.

### `predict`: "Do the math myself"

```toml
[steps.predict]
prompt = "What current do you expect with {choice}?"
unit = "mA"
answer = "(5.0 - 2.0) / R * 1000"     # an expression of the step's variables
tolerance = 0.05                      # relative (±5 %)
optional = true                       # behind a toggle …
toggle_label = "Do the math myself"
toggle_note = "Optional. The meter waits for your prediction."
meter = "dmm1"                        # instrument hidden until the prediction is right
correct_text = "Nailed it. The meter agrees: {meter} mA."
default_hint = "Not quite. Take 5.0 − 2.0 first, divide by R1, then × 1000 for mA."
working = ["V(R1) = 5.0 − 2.0 = 3.0 V", "I = 3.0 V ÷ {R:g} Ω", "I = {amps:.5t} A = {mA} mA"]

[[steps.predict.hints]]               # first match wins, else default_hint
when = "abs(guess - 5000 / R) <= 0.05 * 5000 / R"
text = "Looks like you used the full 5 V. …"
```

Variables available to `answer`, hint conditions and templates: the step's `vars`, the choice
value (`var`), `guess` (the student's number), `meter` (the instrument reading in the step's
unit: × 1000 for `mA`), `answer`, and `mA` / `amps` (= `answer` and `answer / 1000`). With a
toggle the meter stays hidden ("----") until the prediction is right or the working is shown.
`correct_text` should quote `{meter}` (what the instrument really shows, e.g. 13.4 mA through
the meter's burden) rather than `{mA}` / `{answer}` (the formula's value); without a bench the
answer stands in for the reading.

### `measure`: an instrument reading

```toml
[steps.measure]
part = "dmm1"
key = "value"       # reading key (default "value")
scale = 1000        # display scale (A → mA)
unit = "mA"
```

### `table`: "Your measurements"

```toml
[steps.table]
title = "Your measurements"
columns = ["R1", "you said", "meter"]
min_rows = 3                          # distinct values for the checkpoint
passed = "Checkpoint passed"
remaining = "Try {n} more value{s}"
```

A row is recorded per option: with the math toggle on, after a right prediction (`you said`
shows it); with it off, when the meter has settled (`you said` shows `—`). A table implies a
"`min_rows` measurements" goal.

### `quiz`

```toml
[steps.quiz]
question = "A red LED is rated for 20 mA. Which resistor keeps it safe on 5 V?"
options = ["None", "47 Ω", "220 Ω", "10 Ω"]
answer = 2                            # index into options
explain = "(5.0 − 2.0) V ÷ 220 Ω ≈ 13.6 mA …"
```

A quiz implies a "right answer" goal.

### `code`

```toml
[steps.code]
mcu = "u1"
starter = """…"""                     # what the editor opens with
solution = """…"""                    # the reference sketch
image = "firmware/blink.uno.hex"      # its prebuilt image (worked solution, no toolchain)
```

A code step implies a "your sketch is loaded" goal: the app compiles what the student typed
(`bb_lessons::code::compile`; errors come back as diagnostics), flashes it and marks it
loaded. Add `firmware`, `serial_contains`, `pin_frequency` … checks for what the sketch must
do. The tests compile every starter and solution and check the compiled solution against the
step's goals; run `lessons/build-firmware.sh` after changing a lesson sketch so the prebuilt
image matches.

## Expressions and templates

Expressions use the SPICE expression language (`bb_spice::expr`): `+ - * / ^`, comparisons
(`<=`, `==` … are 1 or 0), `&&`, `||`, `abs`, `sqrt`, `exp`, `log`, `pi`, `if(c, a, b)` …
Variable names are case-insensitive.

Templates replace `{name}` or `{name:spec}`; a name that isn't a variable is evaluated as an
expression (`{3/R*1000:s}`), and unknown names stay as written. Specs:

| spec | | 13.636… |
|---|---|---|
| (none), `s` | the design's: ≥ 10 → 1 decimal, ≥ 1 → 2, else 3 | `13.6` |
| `.N` | N decimals | `.2` → `13.64` |
| `.Nt` | N decimals, trailing zeros trimmed | `.5t` on 0.03 → `0.03` |
| `i` | rounded integer | `14` |
| `g` | integer if whole, else shortest | `220` |

## Checks

`checks = [{ type = "…", … }]`. Pins are `part.pin` (`r1.1`, `u1.D13`, `bb1.a5`).

| type | fields | passes when |
|---|---|---|
| `connected` | `a`, `b` | the two pins share a net |
| `not_connected` | `a`, `b` | they don't |
| `part` | `def`, `id`?, `props`? (`{ resistance = 220.0 }`, ±1 %), `count` = 1 | enough such parts exist |
| `prop` | `part`, `prop`, `min`, `max` | the property is in range |
| `voltage` | `a`, `b`? (default ground), `min`, `max` | V(a) − V(b) on the bench, volts |
| `current` | `part`, `element` = `D`, `min`, `max` | \|current\| through the part's SPICE element, amps |
| `reading` | `part`, `key`, `min`, `max` | a device / instrument reading (`dmm1` `value` in V, A or Ω; `scope1` `frequency` …) |
| `led_lit` | `part`, `min_ma` = 1 | the LED carries ≥ min_ma and isn't damaged |
| `led_off` | `part` | < 0.1 mA |
| `damaged` / `healthy` | `part` | the part was destroyed / works |
| `serial_contains` | `mcu`, `text` | the MCU printed `text` (Serial Monitor) |
| `pin_frequency` | `mcu`, `pin`, `hz`, `tolerance` = 0.05 | measured frequency of the pin |
| `pin_duty` | `mcu`, `pin`, `min`, `max` | measured duty cycle (0…1) |
| `firmware` | `mcu` | the MCU runs the step's sketch |
| `world` | `key`, `min`, `max` | a world variable (`air.temp_c`, `pot1.vwc`) |
| `mqtt` | `topic` (filters `+`, `#` allowed), `contains`? | a message reached the bench's broker |
| `phone` | `contains` | the virtual phone's terminal or log shows the text |
| `prediction` | | the step's prediction was right |
| `measurements` | `min` | that many rows in the table |
| `quiz` | | the quiz was answered right |
| `erc_clean` | `strict` = false | no ERC errors (no warnings either when strict) |
| `spice` | `analysis` (a card: `.op`, `.tran 1u 1m`, `.ac dec 50 10 100k`, `.dc …`), `vector` (`v(out)`, `i(v1)`), `at` (time / frequency / sweep value), `stat` = `value` \| `max` \| `min` \| `mag` \| `mag_db` \| `phase_deg`, `min`, `max` | the analysis of the project's Pro netlist gives a value in range (the project's own analysis cards are replaced by this one) |

Bench checks (`voltage` … `phone`) need a running bench; `pin_frequency` / `pin_duty` add
probes when the step starts. Readings are what the instrument shows, so give meters time to
settle (the Handheld DMM autoranges in ~350 ms; run ≥ 1 s).

## Actions

A worked solution is a list of actions, `solution = [{ do = "…", … }]`, replayed in order;
then the bench runs for the step's `run` seconds and the checks are evaluated. The UI can
replay them for "Show me how"; the solver test replays all of them.

| do | fields | |
|---|---|---|
| `add_part` | `def`, `ref`, `props`?, `at` = `[x, y]` | place a part; its id is the lowercase `ref` |
| `remove_part` | `part` | |
| `wire` | `a`, `b`, `color`? | a jumper between two pins (breadboard holes are pins of `bb1`) |
| `unwire` | `a`, `b` | remove the wire(s) directly between two pins |
| `set_prop` | `part`, `prop`, `value` | |
| `choose` | `index` | pick an option of the step's choice |
| `math_mode` | `on` | the "Do the math myself" toggle |
| `predict` | `value`? | enter a prediction (the right answer when omitted) |
| `record` | | record the meter into the table |
| `quiz` | `answer` | |
| `run` | `seconds` | run the bench |
| `press` | `part`, `on` | hold / release a button |
| `position` | `part`, `value` (0…1) | turn a knob |
| `control` | `part`, `key`, `value` | a panel control (`dmm1` `dial`: 0 off, 1 V~, 2 V⎓, 3 mV, 4 Ω, 5 continuity, 6 diode, 7 A, 8 mA, 9 Hz) |
| `world` | `key`, `value` | set a world variable |
| `firmware` | `mcu` | upload the code step's solution (its prebuilt image) |
| `repair` | | "Repair all" |
| `phone_connect` | `name` | the virtual phone connects to the device advertising `name` |
| `phone_terminal` | | open the phone's Bluetooth terminal |
| `phone_send` | `text` | send from the terminal |
| `publish` | `topic`, `payload` | publish to the bench's MQTT broker |

## Validation

`bb_lessons::validate(lesson, library)` reports: unknown step kinds, steps missing the
contents their kind needs, quiz answers out of range, expressions that don't parse, start
circuits that don't load or use unknown parts, checks and choices naming parts that are
neither in the start circuit nor added by an earlier solution, SPICE analyses that aren't
cards, and steps without a worked solution. `cargo test -p bb-lessons` runs it on every
built-in lesson and replays every solution.

## Lesson packs

A lesson pack is a plugin with `"kind": ["lesson-pack"]` and `"provides": { "lessons":
"lessons" }`; that folder has the layout above. Installed packs are found with
`PluginHost::lesson_dirs()` and merged into the catalog with `Catalog::add_packs` (a track
with the same id gains lessons; `LoadedLesson::pack` names the plugin). "Make your own lesson"
(`bb_lessons::editor::Draft`) writes exactly this: `Draft::save_pack(dir, PackInfo)` →
`plugin.json`, `lessons/<track>/track.toml`, `<NN>-<id>.toml`, `<id>.bench.json`;
`Draft::package` zips it as a `.bbplugin`.

## Progress

Per-user progress (steps done, resume step, completed lessons, recorded measurements) lives in
`~/Library/Application Support/Breadbox/lessons/progress.json` (`bb_lessons::Progress`;
`BREADBOX_PROGRESS` overrides the path).
